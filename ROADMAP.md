# SeatMe Roadmap

Working notes on what's shipped, what's built but gated, and what's planned. Not a commitment or timeline — just a place to come back to.

## Shipped

Core seating planner: table types with count/capacity, drag-and-drop guest seating, simulated-annealing auto-generate, seating constraints (must/cannot sit with), group tagging, spreadsheet import, magic-link auth, collaborator sharing (owner/editor/viewer), autosave, conversational AI assistant for making changes by chat.

Floor plan: per-table custom names, four table shapes (round/oval/square/rectangle), free drag-and-drop table repositioning, seated/unseated guest tracking, under-50%-filled table warnings with suggestions.

Guest import: format-tolerant CSV/Excel parsing (first/last name columns, broader header matching, auto-skip declined RSVPs), in-app explainer for exporting from Partiful/The Knot/Bliss & Bone (none of which have a public API, so CSV export is the only path).

Decor tab (free): connect a Pinterest board per event, view first 3 pins with an option to expand to the full board, get a short text decor suggestion (one style recap sentence + 3-5 bullet recommendations) grounded in the board's actual images (Claude vision).

Privacy policy page at `/privacy`, required for the Pinterest app review.

Exports (2026-08-18): "Excel" button on the seating tab downloads a Table/Seat/Guest list in seat order (so seatmates land on consecutive rows) via the existing SheetJS (`xlsx`) dependency. "PDF" button (Map view only) rasterizes the on-screen floor plan via `html2canvas-pro` and assembles it into a PDF sized to fit via `jspdf` — both are new dependencies added to `package.json`, run `npm install` to pick them up. Used `html2canvas-pro` rather than the original `html2canvas` because Tailwind v4's default oklch-based color output breaks the unmaintained original.

Public site (2026-08-18): shared header/footer with an account dropdown (My info / My events / Sign out) present on every page, real homepage with a hero photo, About/Contact/Terms/Privacy pages, `/home` as the signed-in landing page, `/account` for editing first/last name and a recovery phone number (new `profiles` table), and an open feedback box on the About page (`feedback_notes` table, anonymous submissions allowed).

Guest notes & group stats (2026-08-18): optional per-guest note (dietary needs, high chair, wheelchair access, etc.) editable in the Guests tab, shown as a tooltip and a small black dot indicator on that guest's seat in the floor-plan map (kept visually distinct from the separate group-color dot), plus a per-group seated/total breakdown chip row, a map legend, and a "Notes" toggle that highlights every noted seat and lists them for a final pre-print sweep. Raised after comparing SeatMe against iPlan.co.il (a much larger Israeli event-planning platform) — see the RSVP section below for the larger gap that comparison surfaced.

Internal usage dashboard (2026-08-18): `npm run admin:report` generates a local-only, gitignored HTML report (users, sign-up/confirmation status, events owned/shared, in-app activity) — never deployed, needs a Supabase service-role key in local `.env.local` only. Paired with an automatic activation-reminder system: an `access_log` table tracks real in-app usage (once/day/user), and a daily Vercel cron (`vercel.json` → `/api/cron/activation-reminders`) resends a sign-in link to anyone who signed up 24h+ ago and never confirmed, tracked in `activation_reminders` so nobody's reminded twice. `npm run send-activation-reminders` runs the same logic on demand for the current backlog.

Clear tables + agent seat-change fix (2026-08-19): added a "Clear tables" button next to Auto-generate (Seating tab) that unseats everyone and resets the floor plan back to a blank slate — keeps the guest list, groups, table setup, and constraints untouched, so it's a reset for the seating map only, not the whole event. Matching `clear_seating` operation added for the AI assistant. Also fixed a real bug reported the same day: asking the assistant to move/change seats sometimes returned "Here's what I'd suggest." with no checklist and nothing actually proposed — traced to the model occasionally calling its tool with an empty operations list and no real summary, which the server then displayed as if a suggestion had been made. `app/api/agent/route.ts` now only treats a tool call as a real proposal when it contains at least one operation; otherwise it surfaces an honest "couldn't figure out a concrete change, tell me more" message. Also tightened the system prompt to explicitly forbid empty tool calls and bumped `max_tokens` (1536 → 2048) as a safety margin against truncated responses.

Automatic group seating mode (2026-08-19): every group now has a seating mode — "together" (the new default) or "mixed" — that the solver applies automatically on every generate/regenerate, no manual constraints required. Previously, "keep this group together" only worked if you manually added a must-sit-with constraint for every pair of guests in the group (or the AI assistant tried to do that on your behalf, which is what prompted this — asking it to seat a group together made it struggle). Groups default to "together" since that's what tagging a group into existence usually means; click the link/shuffle icon next to a group's name (Guests tab) to flip it to "mixed" for cases like deliberately spreading a friend group across tables. Implemented as a soft cost-function preference in the solver (`buildAutoGroupPairs` in `SeatingPlanner.tsx`), weighted well below explicit user constraints so it never fights a real must/cannot rule and doesn't force an oversized group to impossibly cram onto one table — it just does its best. The AI assistant got a matching `set_group_seating_mode` operation so "seat the Ramirez family together" is now one call instead of N² pairwise constraints.

Conversational assistant caught up to recent features (2026-08-19): the chat assistant's tool schema predated guest notes, RSVP status, and meal choice, so it couldn't touch any of them even though the UI could. Added three operations — `set_guest_note`, `set_guest_rsvp_status`, `set_guest_meal_choice` — end to end (tool schema in `app/api/agent/route.ts`, apply logic in `SeatingPlanner.tsx`, shared types/labels in `lib/agentOperations.ts`), and the context sent to the model now includes each guest's current note/RSVP/meal so it can reference or reason about them. Marking a guest "declined" via chat frees their seat, same as doing it from the Guests tab. Worth a periodic check going forward: any new guest-level or event-level field added to the app should get a matching agent operation (or a deliberate decision to leave it UI-only), or the assistant quietly falls behind the product again.

Site visit tracking, including anonymous visitors (2026-08-19): the existing `access_log` table only ever sees people who already have an account, so there was no visibility into top-of-funnel traffic — how many people land on the homepage, About, Contact, etc. before ever signing up. Found (and finished wiring up) a `site_visits` table that had been created earlier but never actually used anywhere in the app — extended it with `utm_source`/`utm_medium`/`utm_campaign` (so the Instagram bio link or any other campaign link can be attributed) and a `visitor_hash` column, then wired `lib/supabase/middleware.ts` to log every page load of a public marketing page, regardless of sign-in state. Privacy approach: no raw IP address is ever stored — "unique visitors" is estimated from a SHA-256 hash of (IP + user agent + calendar day + a server-only salt), which rotates daily and can't be reversed to identify anyone or track someone across days. Needs a new `VISIT_HASH_SALT` env var (same handling as `CRON_SECRET` — generate it yourself, add to `.env.local` and Vercel; page views still log without it, but "unique visitors" reads 0 until it's set). `npm run admin:report` now shows page views and unique visitors (7d/30d), an anonymous-vs-signed-in split, top pages, top sources/referrers (30d), and a second trend chart alongside the existing one — `buildTrendChart` was refactored to take a `series` argument so both charts share one implementation. Privacy Policy updated with a plain-language description of what's collected and how the hash works.

Usage trend chart (2026-08-19): `npm run admin:report` now also writes `reports/admin-history.json`, appending one data point per day (total users, active users in the last 7 days, total events) each time you run it — re-running on the same day just updates today's entry instead of duplicating it. The report renders this as an inline SVG line chart (no external chart library, so it still works opened offline via file://) above the user table. Needs at least 2 days of runs before a trend line appears; until then it shows a note saying so. Easy to extend with more tracked metrics later — just add fields to `todayEntry` in `scripts/admin-report.mjs` and a matching series in `buildTrendChart`.

RSVP sync + meal choice import (2026-08-19): the guest import parser now recognizes email, RSVP status, and meal/entree columns (in addition to the existing name/group detection), tolerant of varying header wording. Three import modes: "Add to list" and "Replace list" as before, plus a new "Sync RSVPs" mode that matches an uploaded file's rows to existing guests by email (falling back to name), updates their RSVP status/meal choice/email and merges in any new group tags without touching seating or notes, creates a new guest record only for genuinely unmatched rows, and automatically frees the seat of anyone newly marked "declined." Guests declined via import — or manually, by clicking the new RSVP status badge in the Guests tab to cycle Pending → Attending → Declined — are excluded from seated/unseated counts and group stats, though they still show in the full guest list. Meal choice is a freeform text field per guest (no fixed dropdown, since exported menu-choice formats vary by wedding-website source) with a headcount breakdown by choice shown in the Seating tab. Every import is now logged to a new `import_log` table (guest count, mode, whether it carried RSVP/meal data) and surfaced in the internal usage dashboard (`npm run admin:report`) as aggregate stats plus a per-user "files imported / last import" column — answers "how many files people have uploaded."

Mobile UX fixes (2026-08-27): four issues reported after using the app on a phone. (1) Renaming an event was impossible on mobile — the sidebar holding the only editable event-name field is desktop-only (`hidden sm:flex`), and the mobile bottom tab bar has no equivalent; added a small mobile-only event-name input at the top of the event page (`SeatingPlanner.tsx`), visible only below the `sm:` breakpoint since the sidebar already covers desktop. (2) Added a Next/Prev bar at the bottom of each event pane (Tables → Guests & rules → Seating map → Decor ideas) so you can step through in order without hunting for the right tab, on both mobile and desktop. (3) Fixed a real bug where clearing a table's name to retype it would instantly snap back to the auto-generated label — the rename input was bound to the post-fallback computed label instead of the raw typed value, so an empty string never had a chance to register; it now tracks the override directly and only falls back once you click away with nothing typed. (4) Restyled `/events` ("My events," the actual page most mobile sessions land on) to match the rest of the app's redesigned look (Fraunces headings, the same paper/gold/card palette and card-list treatment as `/home` and the marketing pages) — it had been left on its original Georgia-serif, hardcoded-pixel styling from before the 2026-08-18 site redesign, which is what actually read as "not visually aligned" next to everything else.

UX review pass (2026-08-29): a full design/UX audit (`AUDIT_2026-08-29.md`) turned up a dozen issues, all fixed the same day except that destructive actions deliberately got undo instead of a confirmation dialog, per direction. Functional fixes: the table-setup row in the Tables tab overflowed on mobile (now wraps, with small icons distinguishing the "tables" and "seats each" fields); dragging a table on the floor plan only listened for mouse events, so it silently didn't work on a touchscreen (added parallel touch handlers); renaming a table on the map made the AI assistant blind to that name, since its context-builder and its own `seat_guest` apply-logic both built table labels without `tableNameOverrides` — both now take it into account, and `getState()` sends it to the server. Cleanup: deleting a table type used to leave its custom name and saved map position behind as dead data keyed to a now-nonexistent table id; `removeTableGroup` now prunes both. New: an undo system (`pushUndo`/`performUndo` in `SeatingPlanner.tsx`, a matching one in the new `EventsList.tsx`) — removing a guest, table type, group, or constraint, and "Clear tables," all stay instant with no confirmation dialog, but show a brief toast with an Undo button that restores the exact prior state; deleting an event works the same way, except the row is only actually deleted from the database after the undo window (8s) expires, so Undo there needs no round-trip and can't fail. Also new: a "Compact view" toggle and search box on the Guests tab (guest lists over 5 people), search/sort on the events dashboard, an actual notification email when you invite a collaborator (reuses the existing magic-link mechanism instead of silently granting access), and a "Delete event" action on the dashboard. Accessibility: aria-labels on every icon-only button (added once, centrally, via the shared `IconBtn` component plus a few one-off spots), keyboard operability (Enter/Space) for the seat map's seats and the unseated-guest pool — previously mouse/touch only — and a real fix for a measured contrast failure: the site's "muted" secondary-text color only hit 3.4–3.8:1 against its backgrounds (WCAG AA needs 4.5:1 for normal text), so it's now `#736D5F` instead of `#8A8272` (4.65–5.14:1), changed globally across all 20 files that define it. Polish: restyled `InviteForm` to match the rest of the app instead of old hand-rolled inline CSS, gave the login card breathing room from the screen edge on narrow phones, and combined the seating tab's Excel/PDF buttons into one "Export" menu now that the toolbar has six actions. Left open, deliberately: a full WCAG audit (screen reader testing, focus-trap review, live regions for the chat) is a bigger undertaking than one pass covers.

Event setup fields — date, location, max capacity (2026-08-29): new events now get a proper creation form (`NewEventButton.tsx`, opened from "+ New event" on the dashboard) asking for name, date, location, and max capacity up front instead of instantly creating an "New event" placeholder. All four stay editable afterward — date/location/capacity live in the sidebar on desktop and in a compact row under the event name on mobile, autosaved the same debounced way as everything else. `events` gained three real columns (`event_date`, `location`, `max_capacity`, all nullable — a migration, not just JSON in `data`, so they can be queried/sorted on later) rather than being buried in the seating-plan JSON blob. Max capacity is more than just storage: the Tables tab shows a capacity-exceeded warning (mirroring the existing seats-vs-guests one) once active (non-declined) guest count passes it, and the sidebar's guest count turns red the same way the seat count already did when short. The events dashboard cards now show the date and location under the event name when set, so what you enter up front is actually visible again afterward, not write-only.

Fixed: deleted events reappearing (2026-08-29, same day): reported immediately after the delete-event feature shipped — deleting an event made it disappear, but clicking into another event and back to "My events" brought it back. Root cause was the deferred-delete design described above: the actual database delete was scheduled 8 seconds out (so Undo wouldn't need a round-trip), but that timer lives on the `/events` page's client component, and navigating away and back within the window could either lose track of whether it had fired or show a stale cached copy of the list either way. Rewrote it the more boring, reliable way: the delete happens immediately on click, and Undo works by re-inserting the exact deleted row (same id, same data) rather than by cancelling a pending delete. Also added `export const dynamic = "force-dynamic"` to `app/events/page.tsx` so this page — which is mutated from the client constantly (create/rename/delete) — never serves a stale cached render after a client-side navigation back to it, belt-and-suspenders against the same class of bug recurring elsewhere. Known minor gap: if an event has collaborators or a connected Pinterest board, Undo restores the event itself (including the full seating plan) but not those — they're cascade-deleted with the row and aren't captured for restore. Fine for now since it's an edge case; worth revisiting if it comes up.

Table sizing on the floor plan (2026-08-29): two related fixes/features to how tables render on the Seating map. First, a long custom table name (e.g. "The Smith-Jones Family") could make the name-tag input wider than the table itself was sized for, which — combined with a fixed grid spacing that didn't account for it — could crowd a long-named table right up against its neighbor. Round tables now grow their diameter (staying circular, not stretching into an ellipse), square tables grow both sides evenly, and oval/rectangle tables grow just their width, all based on the label's length; the auto-layout grid spacing adapts to the largest table on the plan so this can't cause an overlap. Second, table size now scales up when there are only a few tables on the plan — a single table (or a small handful) renders meaningfully bigger, up to 2.4x, tapering back down to the original baseline size by around 5-6 tables where a bigger size would just cost more scrolling instead of a better view. Guests still render in a ring around each table exactly as before; the seats simply spread further out to match the bigger table.

Location memory for new events (2026-08-29): the "New event" modal's Location field now autocompletes from every location you've used across your own past events (no separate saved-locations table — it's read live from `events.location`, scoped to the signed-in owner). If you type or pick a location that matches a past event which actually has a table setup, a small inline offer appears: reuse that event's table setup (table types, shapes, custom names, and their positions on the map) and its max capacity for the new event. Copying is opt-in via a "Copy setup" toggle, not automatic — it never touches guests, seating assignments, or constraints, only the table configuration itself, so recreating an annual event at the same venue doesn't mean rebuilding the table layout from scratch each time.

Fixed: table auto-scaling overshooting the screen, and seats floating in a circle around rectangular tables (2026-08-29, same day): the "table size scales up when there are only a few tables" feature above shipped as a pure guess based on table count, with no idea how much screen space actually existed — so a single table of 12 could grow to a size where you had to scroll to see everyone seated at it, defeating the point. Table growth is now bounded by the map's actual measured on-screen room (`ResizeObserver` on the container for width, viewport height minus the container's position for height, tracked in `canvasBudget`): a table only grows past its baseline size when there's real room for it to do so without needing to scroll, and never grows past what fits. Separately, and unrelated to the sizing bug: seats were always placed in a circular ring around a table's center regardless of shape, so a square or rectangular table had guests floating in a circle around it instead of sitting along its actual sides — misleading to look at and made it hard to reason about who's really next to whom for "must sit adjacent" rules. Round and oval tables still use a ring (now properly elliptical for ovals, matching the actual w/h instead of a single averaged radius); square and rectangle tables now walk seats evenly around the rectangle's real perimeter instead.

Head-of-table seats for square/rectangle tables (2026-08-29, same day): a follow-up to the seat-placement fix above — square and rectangle tables now reserve exactly one seat at each short end (the "head" and "foot"), visually labeled on the map, with the rest of the capacity split evenly between the two long sides. You assign a guest to the head the same way as any other seat, click or drag — it's just always the same stable seat (index 0) so it can be labeled and found consistently. Side seats are spaced using a margin-from-both-ends formula so none of them land exactly on a corner, at any table size or capacity.

My locations (2026-08-29): a new `/locations` page (linked from the account dropdown next to My info and My events) turns venues from something implicit in past events' `location` text into a real, persistent, editable thing — a new `locations` table (name, total capacity, a default table setup, RLS scoped to the owner same as everything else personal). Each location shows its saved capacity, a summary of its usual table setup (shape/count/seats per table type), and every one of your own events held there (name + date, linking straight through). Adding or editing a location's table setup uses the same shape/count/capacity building blocks as an event's own Tables tab, so what you save here is directly reusable. Deleting a location follows the same instant-delete-with-undo pattern as everything else destructive in this app. This also supersedes part of the location-memory feature from earlier the same day: the "New event" modal's "Copy setup" offer now checks for a saved location profile first (a deliberate, curated default) and only falls back to "copy from your last event at this location" if you haven't saved one — so the more you use My locations, the less guessing the New Event flow has to do.

Venue floor plan uploads (2026-08-29, same day): you can now attach a PDF or image of a venue's actual seat plan in two places — on a saved location (My locations) as the venue's reference default, and separately on each event's own Tables tab, since different events at the same venue can use different physical layouts. Backed by a new public `floor-plans` Supabase Storage bucket (20MB limit, PDF/PNG/JPEG/WEBP only) — public because these are venue reference diagrams, not personal guest data, which sidesteps needing signed-URL machinery while still keeping *uploads* locked down: write access is RLS-scoped per path, `locations/{ownerId}/...` to that owner and `events/{eventId}/...` to that event's owner or editor collaborators (reusing the existing `is_event_owner`/`is_event_editor` functions, so collaborators can attach a floor plan the same way they can edit anything else about the event). When "Copy setup" carries over a saved location's floor plan into a new event, it's an actual server-side copy to the event's own storage path, not a shared reference — removing it later from one place can't delete it out from under the other.

AI table setup suggestions from a floor plan (2026-08-29, same day): answers the natural next question after floor plan uploads shipped — does uploading the plan actually fill in the table setup? Now it can: wherever a floor plan is attached (a saved location or an event's Tables tab), a "Suggest table setup from this floor plan" button sends the file to Claude (vision for images, native PDF support for PDFs — `app/api/floor-plan/suggest/route.ts`, same fetch-to-Anthropic pattern as the existing Pinterest decor suggestions) and asks it to read off the shapes, counts, and approximate capacity of the tables shown. This is a proposal, not an automatic apply — same propose-then-confirm pattern as the AI seating assistant: the suggested table types show in a preview card with a one-line note from the AI, and nothing changes until you click Apply (or Dismiss to discard it). Worth double-checking the AI's read against the actual plan, especially seat counts, which it's estimating from relative table size rather than reading a number off the page.

A-Z guest list jump index (2026-08-29, same day): built for large guest lists (weddings especially, where imports can run 600+) — the Guests tab list now always sorts alphabetically by first name rather than import order, and once a list passes 20 guests, a clickable A-Z strip appears alongside it that jumps straight to the first guest starting with that letter (a "#" bucket catches names starting with anything non-alphabetic). Sits on top of the existing search box, which still works for finding a specific person by name, note, or meal choice.

Floor plan fixtures (2026-08-29, same day): inspired by a UI redesign Esther put together in Claude Design — the seating map can now hold non-seating fixtures alongside tables: Dance floor, Bar, and Stage / band, added from pill buttons in the Tables tab (next to table setup) and freely draggable on the map the same way tables are (mouse and touch). Each fixture is a labeled, colored zone (green/gold/wine, matching the app's existing palette) with no seats or capacity — purely there to help plan the room layout, e.g. so a table doesn't end up backed against the dance floor. Renamable inline, removable with the same undo-toast pattern as everything else destructive, and included automatically in the PDF floor plan export since it's part of the same captured canvas. This ships on SeatMe's current visual style — the fuller visual redesign from that mockup (palette, compact header, dot-based guest seats, richer guest sidebar) is a separate, larger pass, deliberately deferred.

Events reskin, phase 1 — palette (2026-08-29, same day): first step of a multi-phase visual reskin of the events pages, directed by a UI mockup Esther built in Claude Design. Swapped the warm paper/gold/wine palette for a lighter lavender/violet one (`ink #2B2440`, `paper #F5F2FB`, `gold #7454C9`, `goldSoft #E9E1FA`, `line #E3DEF2`, `muted #6B6580` — checked against WCAG AA 4.5:1 same as the earlier contrast fix) across every file under the events pages: the dashboard (`app/events/page.tsx`, `EventsList.tsx`, `NewEventButton.tsx`, `SignOutButton.tsx`) and the planner (`SeatingPlanner.tsx`, `AgentChat.tsx`, `DecorPanel.tsx`, `InviteForm.tsx`). `wine` (danger) and `sage` (success) kept their existing values since they're semantic, not brand colors, and already read well against the new background. Deliberately left untouched: the shared `SiteHeader`/`AccountMenu` (spans the whole site, not just events pages) and the marketing pages/`/locations` — changing those would need a separate, explicit decision since they weren't part of what was asked for. This phase is a pure color-value swap with no layout or component changes, so it's low-risk and reviewable on its own; the bigger structural changes from the mockup (compact header/toolbar, dot-based guest seats on the map with a show/hide-names toggle, richer guest sidebar) are later phases, sequenced this way so Esther can confirm the color direction before more gets built on top of it.

Events reskin — palette reverted (2026-08-29, same day): Esther liked the shape/structure direction the reskin is heading in but not the lavender palette from phase 1 above. Reverted all 8 files back to the original paper/gold/wine/sage colors. Later reskin phases (header/toolbar restructure, dot-based table rendering, guest sidebar) proceed on top of the original palette instead of the lavender one.

Events reskin, phase 2 — compact header (2026-08-29, same day): replaced the event page's vertical left sidebar (name/date/location/capacity fields stacked, vertical tab list, stats list, Share section) and the separate mobile-only header block with one unified horizontal header used at every screen size — a colored initials badge (smart-derived: "Ellis & Rowan" → "E&R", most names → first two initials), the event name and date/venue/capacity inline next to it, a Guests/Tables/Seats/Capacity stat strip, an "All changes saved"-style pill with a status dot, and a Share button that reveals the existing invite form instead of it always taking up sidebar space. On screens sm and up, the four tabs (Tables/Guests & rules/Seating map/Decor ideas) are now horizontal pills under the header instead of a vertical list, with the same violation-count badge as before. The mobile bottom icon tab bar is untouched — kept deliberately, since it's a prior, working thumb-reach fix and this phase is about the header, not mobile navigation. Purely a layout/structure change on the existing (reverted-back) color palette — nothing about the underlying tab content changed.

Fixed: bare max-capacity number in the event header (2026-08-29, same day): phase 2's compact header showed max capacity twice — once as a stray unlabeled number after the date/venue (just "· 12" with no context) and again inside the "Capacity 10/12" stats pill, which read as duplicate/confusing leftover info. Removed the standalone input; the stats pill's max-capacity number is now itself directly editable in place, so there's exactly one spot to see and set it.

Events reskin, phase 3 — compact dot seats (2026-08-29, same day): the Seating tab's Map view now has a "Show names"/"Hide names" toggle (only when a table isn't already showing text — Table view is unaffected). Default stays the full name-tag boxes used everywhere else; switching to "Hide names" swaps each seat for a small colored dot instead — filled with the guest's group color when they have one (falling back to gold), a dashed empty circle for open seats — so a big table's overall shape and fill level reads at a glance instead of needing to scan names. Click/drag/keyboard seating, rule-conflict lines, and head/foot labels all work identically in both modes since only the seat's visual box changed, not its position or interaction handlers. Per earlier decisions in this project, empty seats are never hidden and there's still no capacity-fraction label under the table name in either mode. The map legend adjusts to match (drops the "has a note" dot in compact mode, since that indicator doesn't render on a plain dot).

Events reskin, phase 4 — guest sidebar (2026-08-29, same day): the final phase of the Claude Design-inspired reskin. Every guest row now shows a colored initials avatar (matching their group color when they belong to one) and a one-line context summary under their name — their note if they have one, else their meal choice, else "Declined" or "RSVP pending" when relevant — so the list reads like the mockup's richer per-guest rows instead of a bare name. This teaser line shows in both compact and detailed view; detailed view still has the full editable note/RSVP/meal fields underneath, unchanged. Added RSVP filter chips (All/Attending/Pending/Declined) next to the existing search box and "Compact view" toggle, combining with search the same way the existing A-Z jump index and sort already do. Nothing about the underlying guest data, seating, or existing search/A-Z/notes functionality changed — this is additive visual richness on top of it.

This closes out the events reskin: palette (kept original after Esther's steer), compact header, dot-based map seats with a names toggle, and now the guest sidebar.

## Planned: paid "Design tier"

Idea (raised 2026-08-18): bundle the mockup image generator with shop/vendor recommendations — pointing users to shops that sell items matching their pinned design — behind a paid tier, rather than shipping mockup generation for free.

Open questions to resolve before building:

## Planned: RSVP & guest communications

Raised 2026-08-18 after comparing SeatMe against iPlan.co.il, a much larger Israeli event-planning platform (venue/vendor marketplace + guest tools, 200,000+ events). Their single most-emphasized feature is closing the loop with actual guests — SMS/email RSVP links, live sync back to the seating chart, and bulk guest notifications (save-the-date, arrival instructions, thank-yous).

**Revised after research (2026-08-18):** building a competing guest-facing RSVP *collection* system is probably the wrong move — see `AUDIT_2026-08-18.md` for the full writeup. Zola, The Knot, and Joy all bundle genuinely free RSVP collection into their wedding websites, which most couples already have in place before they find SeatMe; asking guests to RSVP twice is a real adoption cost. What isn't free anywhere, though, is syncing an already-collected RSVP into a *good* seating chart — RSVPify paywalls that specifically ($24/mo+), and Kaiplan sells the combined product directly ($20/mo or ~$100 lifetime). That's the actual gap worth targeting.

Revised direction: an **RSVP sync, not an RSVP form** — let users import the RSVP export their existing wedding website already produces (extends the guest-import work that's already built, rather than standing up guest-facing pages, SMS/email delivery, and a new unauthenticated data model). If a direct-guest touchpoint still feels worth adding later, keep it narrow: a single close-to-the-event headcount confirmation for people who already RSVP'd yes, purely for catering accuracy — not a full RSVP replacement, and not something that competes with the wedding website itself.

**Shipped (2026-08-19):** the sync mechanism described above — see "RSVP sync + meal choice import" under Shipped. What's still open: a possible narrow close-to-the-event headcount confirmation touchpoint (not started, not scoped — revisit alongside the Design tier planning above), and watching real uploads to see whether meal-choice formats vary enough across wedding-website exports to need smarter detection than the current freeform text field.
