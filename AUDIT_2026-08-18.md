# SeatMe Audit — 2026-08-18

A full rundown requested while Esther was away: bugs worth fixing, UX/visual recommendations, roadmap candidates, and a researched pros/cons on direct-to-guest communications. Nothing in this doc has been built yet except where explicitly noted — it's a punch list to review and prioritize, not a changelog.

## Bugs

**Status: the three bugs below are now fixed (2026-08-18, same day).** Left the descriptions as-written for the record.

**Deleting a guest from the UI leaves a "ghost" occupied seat.** The trash-can button next to a guest in the Guests tab (`removeGuest` in `components/SeatingPlanner.tsx`) only removes the guest from the guest list — it doesn't clear their seat assignment or remove any seating constraints that reference them. The seat then shows as permanently occupied by a guest id that no longer exists: it won't appear in the "Unseated" pool, the seated-count stats will overcount, and in Map view there's no obvious way to free the seat (clicking it just re-selects the ghost). It is recoverable — switching to Table view and picking "— empty —" from that seat's dropdown clears it — but that's not discoverable. Notably, the AI chat assistant's own "remove guest" operation *does* clean up both the seat assignment and constraints correctly, so the fix is just bringing the UI button in line with what the AI path already does.

**Deleting a table type leaves the same kind of orphaned seat assignments**, plus never cleans up that table's custom name overrides or saved map position. `removeTableGroup` in the UI does none of this cleanup. The AI assistant's equivalent operation cleans up the seat assignments but still leaves stale name/position entries behind. Net effect: over time, deleting and recreating table types can accumulate dead data in the event's saved JSON, and any guests seated at a deleted table type become invisible-but-still-counted.

**Read-only sharing isn't actually enforced by the database.** The app has a `role` concept (`owner` / `editor` / `viewer`) and the planner does hide edit controls when `role === "viewer"` — but the underlying Supabase row-level-security policy on the `events` table grants *any* member of an event full read/write/delete access, regardless of their assigned role. In practice this is currently low-risk because the invite form only ever creates `editor` rows (there's no way to invite someone as a viewer today at all — see UX section), so there's no live "viewer" to exploit. But it's worth fixing before "invite as viewer" ever gets exposed in the UI, since right now a viewer could bypass the read-only UI entirely with a direct API call and edit or delete the event.

**Already found and fixed this session, noted here for the record:** the auth middleware was redirecting any unauthenticated request to `/login` — including API routes that are supposed to allow anonymous access, like the About page's feedback box, and now the new activation-reminder cron endpoint. This is already patched (`lib/supabase/middleware.ts` now exempts `/api/*` from the redirect and lets each route handle its own auth).

## UX / visual recommendations

**New events are pre-filled with fake sample data, unlabeled.** Every brand-new event starts with ten made-up guests (Ava Chen, Marcus Webb, etc.), two example table types, and a few example seating rules — with nothing in the UI saying "this is a demo, clear it to start your own." A first-time user's honest reaction is likely to be "wait, why are there people I don't know in my wedding?" This is probably the single highest-impact fix in this whole list, since it affects every new user's very first impression of the product. Either label it clearly ("Sample data — edit or clear to start your own") or replace it with a genuinely empty state plus a short inline "here's how this works" hint instead of fake names.

**There's no way to delete an event.** Once created, an event sits on the dashboard forever. Combined with the sample-data issue above, this means test/throwaway events will accumulate with no cleanup path.

**Inviting a collaborator is silent.** Adding someone by email creates their access immediately but never actually notifies them — the only signal is a small line of text telling *you* that they'll get access "next time they sign in." If you don't separately text or email them yourself, they may never know to go create an account. Worth sending an actual notification (reusing the same Supabase email infrastructure as the activation reminders) when someone's added.

**No confirmation or undo on destructive actions.** Removing a guest, a table type, or a group happens immediately on click, with no "are you sure" and no way to undo. Combined with the orphaned-seat bug above, deleting things in the planner currently feels riskier than it should for something people are using to plan a real event.

**The seating map has no pan/zoom for larger events.** It works well at wedding-scale (a few dozen guests, ~10 tables) but will get visually cramped for bigger events — worth a zoom control or minimap once you're seeing feedback from users with 150+ guest lists.

**The events dashboard has no search or sort.** Fine today with a handful of events; will get noisy for anyone managing several.

**Accessibility hasn't had a formal pass** — color contrast (the muted gold-on-cream palette in particular), keyboard navigation through the map, and screen-reader labeling on icon-only buttons are all unchecked. Not urgent, but worth doing before any serious marketing push.

## Direct-to-guest communications: pros, cons, and a recommendation

This was researched specifically because of the overlap concern — here's what's actually out there today.

**The overlap worry is well-founded.** Zola, The Knot, and Joy all bundle genuinely free RSVP collection into their wedding websites, and all three are free, well-known, and typically already in place before a couple ever finds a seating tool — Zola's free tier even explicitly syncs RSVP dietary preferences into its own guest list. If SeatMe builds its own guest-facing RSVP collection, most couples would be asking their guests to fill out two separate RSVP forms — a real guest-experience cost, and a believable reason for a couple to just not bother connecting it.

**But the specific thing SeatMe would be good at — RSVP data flowing straight into an actually good seating chart — is not free anywhere.** RSVPify offers free RSVP collection, same as the wedding-website builders, but paywalls its seating-chart sync specifically, starting at $24/month. Kaiplan sells the combined RSVP-plus-seating-chart product directly, at $20/month or roughly $100 lifetime. iPlan (researched earlier) treats live RSVP-to-seating sync as one of its two flagship features. That's a consistent signal across three different competitors: collecting RSVPs is free and commoditized; keeping a seating chart in sync with them is the part people pay for.

**Recommendation: don't build a competing RSVP collection system — build an RSVP *sync*, not an RSVP *form*.** Concretely, that could mean: letting someone paste in or upload the RSVP export their existing wedding website already produces (Zola, The Knot, and Joy all support exporting guest/RSVP data), and using that to update headcounts and flag no-shows directly in the seating chart — extending the guest-import work that's already built rather than standing up new guest-facing infrastructure. This sidesteps the double-RSVP problem entirely, avoids building and maintaining SMS/email delivery and non-authenticated guest-facing pages (a meaningfully larger lift than anything in SeatMe today), and still solves the actual pain point, which is manual re-entry every time a headcount changes — not the act of asking "are you coming."

If a direct-guest touchpoint still feels worth having later, the narrower and safer version is a single close-to-the-event confirmation nudge for people who already RSVP'd yes — purely a final headcount check for catering accuracy, not a full RSVP replacement, and not something that competes with the wedding website itself.

Sources checked 2026-08-18 (see chat for full list): Zola, The Knot, Joy, RSVPify, and Kaiplan's own marketing/pricing pages.
